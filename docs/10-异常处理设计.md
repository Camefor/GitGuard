# 异常处理设计

## 1. 错误分类

GitGuard 严守 **FailClosed（DR-03）**。所有错误分类决定「用什么退出码阻断」而不是「是否阻断」。

| 类别 | 定义 | 典型示例 | 处理策略 | 对应退出码 |
| --- | --- | --- | --- | --- |
| 用户错误 | 参数、配置、仓库环境错误 | `.gitguard.yml` 版本缺失、非 Git 仓库 | 阻断 + 明确提示修复 | 2 / 13 / 20 |
| 业务阻断 | 命中阻断级规则 | 真实 API Key 泄漏 | 阻断 + 报告 | 1 |
| 依赖失败 | Git CLI 失败、Gitleaks 不可用 | git 命令超时、exit!=0 | **全部 FailClosed 阻断**；Gitleaks 不可用则降级（不属于异常） | 10 |
| 系统错误 | 代码缺陷、未处理分支 | NullReferenceException、Regex 超时、OOM | 阻断 + 收集 trace_id | 11 / 99 |

> **关键原则**：对于 `pre-commit` / `pre-push` 的 Hook 调用链，用户体验排名**低于**安全。宁可用户不方便，也不能让一次异常变成一次放行。

## 2. 异常传播边界

GitGuard 分层架构中的异常传播规则：

| 层 | 允许抛出 | 必须捕获 | 必须转换为 |
| --- | --- | --- | --- |
| `Core.Domain` | `InvariantViolationException`（DR 守卫） | 底层异常不进入此层 | - |
| `Detection` | 规则正则异常（`RegexMatchTimeoutException`） | - | `DetectionException`（带 rule_id） |
| `Application` | `UseCaseException` 系列 | 捕获 `DetectionException` / `GitException` 并封装 | `ScanResult(Failed, exit_code)` |
| `Infrastructure` | `GitException`、`SqliteException`、`IOException` | - | 保留原始异常，Application 层封装 |
| `Cli` | - | 捕获所有未处理异常 → `UnknownErrorExitCode(99)` | 用户友好信息 |

- **Core.Domain 不能依赖 `Microsoft.Data.Sqlite`**，更不能 catch `SqliteException`。
- **Infrastructure 不能抛纯粹的 `Exception`**；必须用项目定义的异常类型（`GitException` / `SqliteException` 包装）。
- `GitException` 定义在 `GitGuard.Core` 根命名空间：`Cli` 层需要 `catch` 它并映射退出码，而 `Cli` 不得引用 `Infrastructure`；错误码经 `ErrorCode` 属性携带（取自 §4 登记表），并附 `ExitCode` / `StandardError` 供诊断。

## 3. 全局异常处理

`GitGuard.Cli.Program` 的入口：

```csharp
try
{
    return await rootCommand.InvokeAsync(args);
}
catch (OperationCanceledException)
{
    stderr.WriteLine("已取消。");
    return 12; // 取消在 CLI 上作为超时的变体
}
catch (ConfigurationException ex)
{
    reporter.Report(ex);
    return 13;
}
catch (GitException ex)
{
    reporter.Report(ex);
    return ex.ErrorCode == GitException.NOT_A_GIT_REPOSITORY ? 2 : 10;
}
catch (DetectionException ex)
{
    reporter.Report(ex);
    return 11;
}
catch (Exception ex) when (IsUnexpected(ex))
{
    reporter.ReportCrash(ex); // 脱敏后登记到 audit + stderr
    return 99;
}
```

**禁止写法**：

- `catch (Exception) { return 0; }`（违反 FailClosed）
- `catch (Exception) { throw; }` 作为「包装」唯一动作（没有分类意义）
- 吞异常（空 catch 块）

## 4. 错误响应契约

遵循 `06-API接口设计.md` §4.4 的错误 JSON Schema。错误码来自已登记的枚举：

| error_code | exit_code | 场景 |
| --- | --- | --- |
| `NOT_A_GIT_REPOSITORY` | 2 | 当前目录不是 Git 仓库 |
| `WRITE_PERMISSION_DENIED` | 3 | 无法写 Hook 文件 |
| `UNKNOWN_HOOK_PRESENT` | 4 | Hook 存在但不是 GitGuard 托管，需要 `--force` |
| `GIT_COMMAND_FAILED` | 10 | Git 子进程非零退出、超时或无法启动 |
| `DETECTOR_FAILED` | 11 | 任何 `IDetector` 抛异常 |
| `SCAN_TIMEOUT` | 12 | 整体扫描或单规则超时 |
| `CONFIG_INVALID` | 13 | `.gitguard.yml` 解析失败或违反硬下限 |
| `ALLOWLIST_VALIDATION_FAILED` | 20 | 白名单 add 参数不合法 |
| `ALLOWLIST_NOT_FOUND` | 21 | 要删除的条目不存在 |
| `AUDIT_RUN_NOT_FOUND` | 30 | 查询不存在的 run_id |
| `AUDIT_EXPORT_FAILED` | 31 | 审计导出 IO 失败 |
| `RULE_NOT_FOUND` | 40 | 规则 ID 不存在 |
| `INSTALL_IN_PROGRESS` | 50 | 已有并发 install 持锁 |
| `UNKNOWN_ERROR` | 99 | 未分类异常 |

## 5. 降级策略

| 失败点 | 检测方式 | 降级分支 | 用户提示 |
| --- | --- | --- | --- |
| Gitleaks 可执行文件缺失 | 启动期 PATH 探测 | 禁用 `GitleaksAdapter`，继续用内置规则 | `Information` 级日志："Gitleaks 适配器已禁用" |
| `fingerprint.salt` 读取失败 | 文件 IO | 内存生成临时 salt，警告 | `Warning`: "指纹盐临时生成，白名单可能需要重登记" |
| 单个 `IDetector` 异常 | catch | **不降级，直接 FailClosed**（exit_code 11） | 列出失败规则 ID，建议暂时 `enabled: false` 并提交 Issue |
| Regex 超时 | `RegexMatchTimeoutException` | 禁用该规则，继续其他规则**但本次 ScanRun 结果 = Failed** | 建议修复或移除该正则 |
| SQLite 写失败 | catch | 当前扫描结果照常返回，但审计日志写入失败将被记为 `AuditWriteFailed` 事件（下次启动尝试补写） | `Warning`: "审计写入失败" |
| 日志文件写满 | IO 异常 | 转到 stderr，不阻断业务 | `Warning` |
| 配置文件违反硬下限（降级 critical 为 allow） | `PolicyValidator` | 启动失败 FailClosed | `Error`: 指出哪条规则违规 |

> **FailClosed 不是降级**：以上「不降级」项必须阻断。

## 6. 重试与熔断

| 场景 | 策略 |
| --- | --- |
| SQLite `BUSY` 错误 | 指数退避重试 3 次（50ms, 100ms, 200ms） |
| Git 子进程超时 | **不重试**，直接 FailClosed（避免对慢 Git 环境放大延迟） |
| Gitleaks 子进程异常 | 不重试；适配器直接报告 `DETECTOR_FAILED` |
| Regex 正则超时 | 不重试；禁用该规则 + FailClosed |

MVP 不引入熔断器（本地短生命周期无必要）。

## 7. 前端错误呈现（CLI 终端）

- 终端输出遵循「醒目 + 简洁 + 可操作」：

  ```text
  ❌ GitGuard 扫描失败（exit_code=13）
     错误码：CONFIG_INVALID
     原因：.gitguard.yml 第 15 行：policy.critical 不能设置为 allow（硬下限）
     参考：docs/模块设计/Policy.md §7
     trace_id：XK3P-9A2L
  ```

- **禁止**：输出完整 stack trace（除非 `--verbose`）。
- **禁止**：在 message 中暴露文件路径的用户名部分。
- **允许**：输出 `trace_id`，用户反馈 Issue 时引用。
- **彩色策略**：异常用红色、警告用黄色、成功用绿色；`--no-color` / `NO_COLOR` 环境变量 / 非 TTY 时自动禁用。

## 8. 排查支持

- 每次扫描生成唯一 `run_id`（UUIDv7），错误输出中附带。
- `gitguard audit view <run_id>` 可查看该次扫描的完整脱敏事件链。
- `--verbose` 把日志级别降到 `Debug`；`--verbose --trace` 到 `Trace`。
- 崩溃信息写入 `~/.local/share/gitguard/crash/<timestamp>-<trace_id>.log`（已脱敏）；用户可随 Issue 一起提交。
