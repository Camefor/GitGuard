# 开发规范

## 1. 适用范围

本规范适用于 GitGuard 仓库全部源代码、测试代码、迁移脚本、Shell / PowerShell 脚本、Markdown 文档。例外必须在 PR 描述中说明原因与影响范围。

## 2. 开发环境

| 工具 | 版本 | 说明 |
| --- | --- | --- |
| .NET SDK | 10.0 LTS | 本地与 CI 一致 |
| Git | ≥ 2.9 | 本机工具与被测试的 Git 版本保持一致 |
| IDE | Rider 2026.1 / Visual Studio 2026 / VS Code（可选） | 推荐 Rider；统一通过 `.editorconfig` 强制风格 |
| 代码分析 | StyleCop.Analyzers、Microsoft.CodeAnalysis.NetAnalyzers、Roslynator | 作为 NuGet 包引入；CI 启用 `TreatWarningsAsErrors` |
| 测试 | xUnit v3、FluentAssertions、Shouldly（二选一，统一使用 FluentAssertions） | - |
| 覆盖率 | coverlet.collector + ReportGenerator | - |
| 本地 Hook | 本项目使用 GitGuard 自身 + `dotnet format` | 冷启动阶段先用 `pre-commit` 跑 `dotnet format --verify-no-changes` |

## 3. 工程结构

- 目录结构与依赖方向：详见 [`03-系统架构设计(SAD).md`](<./03-系统架构设计(SAD).md>) §5.1。
- 新建模块：
  - 新增项目先在 `GitGuard.sln` 中注册；统一通过 `Directory.Packages.props` 做中央包管理。
  - 跨模块通信必须通过 `GitGuard.Core.Abstractions` 定义的接口；禁止直接引用具体实现。
- 禁止：
  - `src/` 内任意项目直接引用 `tests/`。
  - `Cli` / `Desktop` 项目直接引用 `Infrastructure`（必须经 `Application`）。
  - 任何项目引用 `System.Net.Http` / `System.Net.Sockets`（DR-01；通过 Analyzer 规则强制）。

## 4. 编码规范

### 4.1 通用

- **命名**：
  - 类型 / 方法：PascalCase；私有字段 `_camelCase`；常量 `UPPER_SNAKE_CASE`。
  - 异步方法必须以 `Async` 结尾；接口以 `I` 开头。
  - 规则 ID 命名：`^(GGD|USR|GLK)/[A-Z]+/[A-Z0-9_-]+$`，领域术语对齐 `04-DDD §8`。
- **空值与可选**：`<Nullable>enable</Nullable>` 全开；禁用 `!`（null-forgiving operator）除非配套注释解释原因。
- **时间与时区**：所有时间以 UTC 存储（`DateTimeOffset`），显示层按用户区域转换；禁止使用 `DateTime.Now`。
- **异步与并发**：
  - CLI 顶层返回 `Task<int>`；避免同步阻塞异步（`.Result` / `.Wait()` 全部禁用，CodeAnalysis 配置为 Error）。
  - 并发集合优先选 `ConcurrentDictionary` / `ImmutableArray`。
- **异常**：
  - 自定义异常继承 `GitGuardException`；按 §10 的 Error Code 契约。
  - 禁止 `catch (Exception)` 并返回 0（违反 DR-03）。
  - 禁止吞异常。
- **集合与不可变**：
  - 跨模块的「只读查询结果」用 `ImmutableArray<T>` / `IReadOnlyList<T>`。
  - `List<T>` 作为内部临时结构可以用，但不作为公开签名返回类型。

### 4.2 规则正则

- 所有规则正则必须：
  - 显式 `RegexOptions.Compiled | RegexOptions.CultureInvariant`。
  - 显式 `Regex.MatchTimeout = TimeSpan.FromMilliseconds(200)`。
  - 通过 `BuiltinRules.yaml` 加载；不得硬编码在 C# 中。
- ReDoS 用例集：`tests/GitGuard.Detection.Tests`（`DetectorRobustnessTests`）对所有内置规则做对抗性输入测试，并覆盖 200ms 超时的 FailClosed 契约。

## 5. 注释与文档

- 注释写**为什么**，不写**是什么**。
- 核心业务逻辑（尤其是 DR 实现、FailClosed 分支、脱敏流水线）必须有注释说明「这里对应 DR-X / FR-X / ADR-X」。
- 公共 API 使用 XML 文档注释，`<Nullable>` 覆盖的方法注意 `null` 行为的 `<returns>` 说明。
- **禁止**：
  - 对简单赋值或字段加「赋值 xxx 字段」这类无价值注释。
  - 把 PR 描述、issue 链接写进代码注释（信息会腐坏）。
  - 复制粘贴 ChatGPT 的解释语气（如"这段代码的作用是..."）。

## 6. 前端规范

Avalonia 桌面端（P3）：

- View 不写业务逻辑；所有逻辑进 ViewModel。
- 使用 `CompiledBindings`，避免反射 Binding 的运行时成本。
- 国际化：禁止在 `.axaml` 中硬编码用户可见文本；统一走 `Resources/zh-CN.axaml`。
- 深色/浅色主题通过 `ThemeVariant` 实现，不手写两套样式。

## 7. 后端规范

此项目「后端」即 `GitGuard.Core / Application / Infrastructure`：

- **Application** 层：按 Use Case 命名，一个 Use Case 一个类。
- **Infrastructure** 层：
  - `GitAccess`：通过 `System.Diagnostics.Process` 启动 `git`；禁止用 LibGit2Sharp 等 Native 依赖。
  - `SqliteAuditStore`：使用参数化查询；禁止字符串拼接 SQL。
- **Domain** 层：只定义值对象、聚合、规则；无 IO。

## 8. 数据库规范

- 迁移文件命名：`VNNN_<kebab-description>.sql`，`NNN` 从 `001` 开始，不复用、不跳号。
- 禁止：`DROP COLUMN`（SQLite 支持有限）；禁止长锁 DDL。
- 新增索引必须在 `05-数据库设计.md` §5 登记。

## 9. 测试规范

- 单元测试覆盖率目标：核心规则/策略/领域服务 ≥ 85%；Infrastructure ≥ 70%；CLI 层 ≥ 60%。
- 命名：`<MethodName>_<Scenario>_<Expectation>` 或 BDD 风格 `When_<State>_Should_<Behavior>`。
- 禁止：
  - 测试代码引用生产代码的 `internal` 成员（除非通过 `[InternalsVisibleTo]`，且仅给测试项目开放）。
  - 在生产代码中保留测试用后门。
- 「金丝雀 Token 测试」（`TC-DR-02-01`）必须在 CI 的全路径跑一次。
- 详见 `16-测试方案.md`。

## 10. 版本控制

### 10.1 分支策略

- 主分支：`master`（与远端 `origin/master` 一致）。
- 单人维护阶段允许在 `master` 上直接提交并推送；多人协作或高风险改动使用 `feat/GGD-NNNN-<kebab-desc>`、`fix/GGD-NNNN-<desc>`、`docs/GGD-NNNN-<desc>` 分支并通过 PR 合并。
- 禁止强制推送（`git push --force`）；主分支受 GitGuard 自身保护：安装 pre-commit / pre-push 后再提交。

### 10.2 提交规范

遵循 Conventional Commits，提交与 `AGENT-GUIDE.md` 任务台账一一对应：

```
<type>(<scope>): <summary> (GGD-NNNN)

<可选正文：说明动机、关键决策与影响>

<可选 footer，如 Refs / BREAKING CHANGE>
```

- `type` 枚举：`feat / fix / docs / refactor / test / chore / perf / build / ci`。
- `scope` 示例：`core / detection / cli / hook / policy / audit / infra / tests / desktop / docs / ci`。
- `summary` 使用英文祈使句，首字母小写，不加句号；含任务 ID 后长度 ≤ 72 字符。
- **任务 ID 必填**：标题末尾附 `(GGD-NNNN)`；无对应任务的维护性变更须在正文说明原因。
- **正文**：解释「为什么」和影响，不复述 diff；可使用中文。
- **原子性**：一次提交只包含一个任务；禁止夹带无关文件、构建产物、`.env`、密钥或本地配置。
- **可回滚**：提交应可独立回滚，不把格式化、重命名与行为变更混在同一提交。
- **提交前检查**：`git diff --cached` 确认暂存内容；`git status` 确认工作区无遗漏或误入文件；文本文件编码与行尾符合 §12。

### 10.3 PR 评审要点

- [ ] 本 PR 只包含本任务范围（无夹带）。
- [ ] 同步更新设计文档（PRD/SRS/SAD/模块设计 等）。
- [ ] 补齐测试（含金丝雀 Token、FailClosed 路径）。
- [ ] CI 通过（`dotnet build` + `dotnet test` + `dotnet format --verify-no-changes`）。
- [ ] 本次变更不违反 ADR-0001 ~ ADR-0003 的决策，否则需补 ADR。
- [ ] AGENT-GUIDE 任务状态更新。

## 11. 完成定义（DoD）

每个任务合入 `main` 前必须满足：

- [ ] 功能满足 FR 验收（引用 FR-NNN）。
- [ ] 单元 / 集成 / 场景测试覆盖通过。
- [ ] 文档同步更新（设计、CLI 契约、数据库、测试、模块设计）。
- [ ] CI 全绿。
- [ ] `AGENT-GUIDE.md` 任务状态更新为 `DONE`。
- [ ] 若引入新依赖，`Directory.Packages.props` 已集中登记并说明用途。

## 12. 文本文件格式

- 编码：**UTF-8 with BOM**（Markdown / `.cs` / `.axaml` / `.ps1` / `.sh` 默认）。
- 行尾：**CRLF**（除 JSON、YAML、`.editorconfig`、GitHub Actions `.yml` 等现代配置按惯例，CRLF/LF 二选一但本仓库统一为 CRLF）。
- 空白：行尾不留空白；文件末尾保留单一换行。
- `.editorconfig` 作为兜底；在仓库根目录维护。
