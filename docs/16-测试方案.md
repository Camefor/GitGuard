# 测试方案

## 1. 测试策略

GitGuard 作为**安全工具**，测试策略以「真实场景覆盖」优先于「覆盖率数字」：

1. **测试驱动不变式**：DR-01 ~ DR-06 的每一条都必须有独立测试用例（即使正常 FR 测试已覆盖）。
2. **FailClosed 用故障注入验证**：模拟 Git 命令失败、Regex 超时、SQLite 锁定，确认退出码 ≥ 10。
3. **测试左移**：核心规则正则在合入前跑 ReDoS 用例集；配置文件 Schema 校验跑在单测里。
4. **真实 Git 集成**：E2E 测试通过 `Fixture` 启动 `git init` 临时仓库，调用真实 `git`、`gitguard` 二进制，验证 Hook 行为。
5. **金丝雀 Token 自检**：所有本地审计 / 日志路径不得包含 `AKIA_SENTINEL_${run_id}` 原文——CI 全路径跑一次。

## 3. 测试用例命名与追溯

- 单元/集成测试类：`<ClassUnderTest>Tests`。
- 测试方法：`<Method>_<Scenario>_<Expectation>` 或 `When_<State>_Should_<Behavior>`。
- 契约 / 场景 / DR 用例：显式用「TC-\*」命名注释（供文档追溯），例如：

  ```csharp
  // TC-DR-04-01
  [Fact]
  public async Task PreCommitScan_ShouldNotReadWorkingTreeFiles()
  { ... }
  ```

- 每个 FR / NFR / DR 必须至少有一条 TC 追溯；追溯矩阵在 `02-SRS §8`。

### 5.1 Hook 框架兼容矩阵（NFR-A-001）

实现：`tests/GitGuard.E2E.Tests/HookFrameworkCompatibilityTests.cs`（`RealFrameworkInstall_CoexistsWithGitGuard`，Theory 参数 `husky` / `lefthook` / `pre-commit`）。三种框架均在临时仓库中真实安装：Husky v9（`npm install husky@9` + `husky init`，相对 `core.hooksPath=.husky/_`）、lefthook v2（`lefthook install` 写入 `.git/hooks/pre-commit`）、pre-commit 4.x（`pre-commit install` 写入 `.git/hooks/pre-commit`）。

| 用例 ID | 场景 | 预期 |
| --- | --- | --- |
| TC-COMPAT-01 | 真实框架安装后执行 `gitguard install` | 框架 Hook 备份为 `.local.bak`，目标 Hook 替换为 `gitguard-managed` 分发脚本；Husky 仓库不写入默认 `.git/hooks` |
| TC-COMPAT-02 | 正常提交 | GitGuard `PreCommit` 扫描 `Clean` 且只执行一次；框架 Hook 同时执行 |
| TC-COMPAT-03 | 暂存区含金丝雀密钥 | 提交被阻断（退出码 1），框架 Hook 仍执行；审计记 `Blocked`，金丝雀原文不落盘 |
| TC-COMPAT-04 | `gitguard uninstall` 后提交 | 框架 Hook 逐字节还原、备份被消费，后续提交不再触发 GitGuard 扫描，框架 Hook 恢复独立执行 |

> Husky 兼容要点：`.husky/_/h` 按 `$0` 推导 `.husky/<hook>`；分发脚本对 POSIX sh 形态的备份以「原 Hook 路径作为 `$0`」执行（`sh -c` + source），避免备份名 `.local.bak` 使 Husky 解析到不存在的文件而静默跳过。

| 全量扫描吞吐 | `benchmarks/run.sh throughput`，100 MiB 语料，进程内检测器管线 | ≥ 20 MB/s | P50 26.08 MB/s，达标 |

超阈值 → 用 `gitguard scan --staged --verbose` 查看 `Scan.RuleTiming` 规则级耗时（`rule_id` / 求值次数 / 命中次数 / `duration_us`），优化或禁用高耗规则；逐行匹配细节仍用 `--verbose --trace`。

完整方法、环境快照与结果解读见 `benchmarks/README.md`。

## 8. 安全测试

- **ReDoS 用例集**：对所有规则正则跑 10 条已知灾难性回溯模式；超时即判定测试失败。

## 11. 持续集成

- **性能工具**：`benchmarks/GitGuard.Benchmarks` 为无第三方依赖的自研 harness；进程级场景以发布版 Native AOT 可执行文件测量端到端墙钟耗时，吞吐场景在进程内驱动检测器管线。基准不作为 CI 门禁，报告输出 PASS / FAIL 与统计量（`GGD-0020`）。
- **流水线阶段**：`.github/workflows/ci.yml` 实现 `restore → build → format → unit（Core / Detection）→ integration（Infrastructure / Application）→ contract（Cli）→ scenario（E2E）`，并设独立 `hook-compat` 作业（`windows-latest`，安装 Node 22 + pre-commit 后运行 `TC-COMPAT-*`）、`git-compat` 作业（Git 2.9.3 / 2.40.1 / 最新稳定版的 E2E 矩阵）与 `desktop-package-smoke` 作业（Windows MSIX 构建 → 解包 → `smoke-test.ps1`，`GGD-0047`）；`.github/workflows/release.yml` 在 `v*` Tag 或手动触发时先解析版本，再执行 CLI Native AOT 矩阵（`win-x64` / `linux-x64` / `osx-arm64` / `osx-x64`）与桌面安装包作业（Windows MSIX / macOS DMG / Linux AppImage），各平台原生桌面作业下载对应 CLI 产物完成发行形态冒烟（macOS x64 交叉产物除外）。
- **Windows 单平台**：测试流水线当前仅在 `windows-latest` 上执行；macOS / Ubuntu 测试矩阵与 Linux DR-01 `strace` 作业不再计划，CI 不验证跨平台单元 / 集成兼容性（`GGD-0028` 已取消）。桌面安装包由 Release 在 macOS / Ubuntu runner 上构建并冒烟，覆盖发行形态的三平台可启动性。
- **失败阻断策略**：
  - 单元 / 集成 / 场景测试任一失败 → 阻断合入。
  - 性能测试仅在 MINOR 发布节点阻断；日常 PR 失败只警告。
- **测试报告归档**：各测试项目经 MTP 内置 xUnit reporter 输出 TRX、经 `Microsoft.Testing.Extensions.CodeCoverage` 输出 Cobertura 覆盖率，统一落盘 `artifacts/test-results/<project>/`；`build-test` 与 `hook-compat` 作业均在 `if: always()` 下分别上传 `test-results-windows` / `test-results-hook-compat-windows` 构件（保留 30 天），失败时同样归档以便定位。
- **Analyzer 结果**：StyleCop + Roslynator 发现的任何 Error 级问题阻断（Release 构建 `TreatWarningsAsErrors`）。
- **格式门禁**：`build-test` 作业在 Build 后执行 `dotnet format GitGuard.sln --verify-no-changes --no-restore`；GGD-0018 已修复此前 83 处 IDE1006 命名规则冲突（src 与 tests 均有），并为架构边界守卫补充 `DesignTimeBuild` 条件，避免 `dotnet format` 工作区加载时因传递项目引用误报。
