# 误报治理指南

## 1. 目的与适用范围

本指南面向 GitGuard v0.2 的项目负责人、安全管理员与日常开发者，解决三个问题：

1. 一条命中到底算不算误报，如何留下可复核的证据；
2. 误报应该用 `exclude`、白名单、基线文件还是策略降级处理；
3. 如何用现有 CLI 命令统计误报率，支撑 RoadMap §2.2 的真实项目试用验收。

适用范围：

- GitGuard v0.2 的 `scan --staged` / `scan --push` / `scan --all` 三条扫描链路，以及 `audit` / `allowlist` / `rules` 管理命令。
- 本文的验收指标只在**真实项目试用**场景使用，不替代 `16-测试方案.md` §12 的 MVP 自动化场景。
- RoadMap §2.2 的退出条件「在至少 1 个真实中等规模项目（10+ 开发者）试用，首周误报率 ≤ 10%」由用户亲自执行与验收；本文提供口径、模板和可复现命令，不把该条件标记为已完成。

## 2. 术语与判定口径

### 2.1 基本单位

| 术语 | 含义 |
| --- | --- |
| Finding | 一次扫描中由某条规则命中的一条记录，对应审计导出 CSV 的一行（`finding_id` 非空） |
| 运行（Run） | 一次完整的扫描，对应 `scan_runs` 的一行与一个 `run_id` |
| 唯一问题 | 按 `(rule_id, fingerprint)` 去重后的命中，代表「同一个值被同一条规则重复命中」；用于问题级统计 |
| 阻断级 Finding | 在试用期冻结的策略下动作为 `block` 的 Finding；默认策略下等价于 `Critical` / `High` |
| 检出值 | 被规则匹配到的原始敏感文本；只允许在本地核对，禁止写入报告、工单或统计表 |

> 审计导出与 `audit view` 只包含 `snippet_masked` 与 HMAC 指纹，不包含原始值。需要确认是否为真实凭据时，应在本地代码 / 环境中核对，不得把原文复制到任何共享文档。

### 2.2 分类定义

对每条待评审的 Finding，只允许以下三种分类：

| 分类 | 判定标准 | 处理要求 |
| --- | --- | --- |
| **TP（真实命中）** | 命中值是真实可用凭据、真实个人信息，或虽为测试数据但可用于访问真实系统 | 按安全事件流程整改；真实凭据先轮换再清理历史，禁止用白名单掩盖 |
| **FP（误报）** | 命中值是示例、占位符、合成测试数据、公开文档值、已失效值，或规则语义与实际内容不符 | 按 §5 选择最小治理手段，并登记原因 |
| **Pending（待定）** | 暂时无法确认值真实性，或需要业务方 / 数据所有者确认 | 记录责任人与截止时间；Pending 不计入误报率分子，但必须单独报告占比 |

判定注意：

- 位于测试目录不等于自动 FP。若测试夹具中的 Token 仍可访问真实环境，按 TP 处理。
- 公开文档中的官方示例值（如 AWS 文档的 `AKIA...EXAMPLE`）按 FP 处理。
- 被白名单或基线放行的 Finding 仍然保留在报告中；评估检测器精度时仍按原始命中分类，不能因为「已经放行」就改为 TP。

### 2.3 度量指标

试用期统一使用以下指标。指标分母只统计 `scan_type` 为 `PreCommit` / `PrePush` 的运行，避免历史全量扫描的存量噪声稀释首周体验数据。

| 编号 | 指标 | 公式 | 用途 |
| --- | --- | --- | --- |
| M1 | **阻断级问题误报率（验收主指标）** | `FP_block_unique / (TP_block_unique + FP_block_unique)` | 对应 RoadMap「首周误报率 ≤ 10%」；按 `(rule_id, fingerprint)` 去重 |
| M2 | 全量问题误报率（辅助） | `FP_all_unique / (TP_all_unique + FP_all_unique)` | 观察 Medium / Low 规则的整体精度 |
| M3 | 阻断级事件误报率（辅助） | `FP_block_rows / (TP_block_rows + FP_block_rows)` | 反映开发者实际被打断的次数；重复命中会被重复计数 |
| M4 | 单规则误报率（治理） | `FP_rule / (TP_rule + FP_rule)` | 定位需要调整上下文、禁用或替换的规则 |
| M5 | 待定率（数据质量） | `Pending / 全部待评审唯一问题` | 高于 5% 时 M1 视为暂定，必须补完评审 |

口径约束：

- **去重键**：`(rule_id, fingerprint)`。同一指纹被不同规则命中时分别统计；同一规则下同一值出现在多个文件 / 多次提交只算一个唯一问题。
- **阻断集合**：默认策略下 `Critical` + `High`；若项目修改了 `policy`，必须在试用记录中冻结并写明映射，统计时以该映射为准。
- **策略冻结**：试用首周不得临时修改 `policy` 或大量增删规则；确需变更时记录变更时间，并从变更后重新开始一个 5 个工作日窗口。
- **Pending 处理**：M1 分母不含 Pending；M5 > 5% 时先补评审，不宣布验收结果。
- **样本量**：单规则评审样本少于 5 条时，只看 FP 绝对数与具体案例，不据此对规则下结论。

> `audit export` 的 CSV / JSON **不包含逐条动作字段**。因此统计时用「Finding 的 `severity` + 试用期冻结的策略映射」还原阻断级集合；不要把 `run.result = Blocked` 直接当成「该运行所有 Finding 都是阻断级」。

## 3. 规则分级与默认策略

### 3.1 规则库概况

v1.0 进行中，内置规则共 **45 条**：

| 类别 | 规则数 | Critical | High | Medium | Low |
| --- | ---: | ---: | ---: | ---: | ---: |
| Secret | 21 | 11 | 9 | 1 | 0 |
| Privacy | 9 | 0 | 3 | 5 | 1 |
| LocalPath | 7 | 0 | 0 | 1 | 6 |
| Url | 8 | 0 | 6 | 2 | 0 |
| **合计** | **45** | **11** | **18** | **9** | **7** |

完整规则清单见 §9 附录 A。Gitleaks 适配器启用后动态产生的 `GLK/SECRET/*` 规则不计入这 45 条。

### 3.2 严重度与默认策略

| 严重度 | 默认动作 | 含义 | 典型规则 |
| --- | --- | --- | --- |
| Critical | `block` | 高置信度真实凭据或私钥，必须立即处理 | AWS Access Key、GitHub PAT、PEM 私钥、Stripe / GitLab / OpenAI Key |
| High | `block` | 高置信度凭据、带密码连接串、Webhook、身份证 / 银行卡等 | Generic Password、DB Connection String、Slack Token、CN ID Card 18 |
| Medium | `warn` | 需要人工判断的隐私或网络信息 | JWT、手机号、SSN、私网 IP、内网域名 |
| Low | `warn` | 噪声较高的本地路径与邮箱 | Unix / Windows 用户目录、`~/` 路径、邮箱 |

硬约束：

- `policy.critical: allow` 是非法配置，加载期直接以退出码 13 拒绝（配置加载器硬下限）。
- 降低某一严重度的动作（如 `high: warn`）会影响该级别下**所有规则**，属于全局策略变更，必须经过项目负责人审批并记录。
- 策略降级与规则禁用会在审计库产生 `PolicyOverride` 事件（`SEVERITY/<Severity>` 合成 ID，或规则 ID → `Allow`），可作为复核依据。

### 3.3 规则分级的使用原则

1. **先修内容，再调规则**：示例值改成明显的占位符、测试夹具改成合成值、真实配置改用环境变量，通常比调规则更彻底。
2. **不要为了消灭误报全局降级**：把 `high: warn` 会让所有 High 规则失守；优先使用规则 + 路径的窄白名单。
3. **规则级问题优先规则级处理**：某条规则在特定目录持续误报时，先尝试 `disabled_rules` + 自定义更严格规则；只有确认规则整体不可用时才全局禁用。
4. **自定义规则不替代校验器**：`rules.custom` 不支持 `luhn` / `cn-id-checksum` 等内置声明式校验器；涉及身份证、银行卡等校验位的规则应保留内置规则，通过上下文或窄白名单治理。
5. **Gitleaks 噪声单独归因**：`GLK/*` 命中与内置规则重复时由系统按 `USR > GLK > GGD` 去重；若 Gitleaks 独有规则误报，用 `disabled_rules` 精确禁用该 `GLK/` 规则，而不是关闭整个适配器。

## 4. 常见误报来源与首选处置

处置顺序固定为：**修复内容 → 精确排除 → 窄白名单 → 基线（仅历史存量）→ 规则 / 策略调整**。越靠后影响面越大，审批要求越高。

| # | 场景 | 典型规则 | 误报原因 | 首选处置 | 次选 / 注意 |
| --- | --- | --- | --- | --- | --- |
| 1 | 官方文档中的示例 Access Key | `GGD/SECRET/AWS-AKID` | 示例值符合 AKIA 格式，但并非真实凭据 | `allowlist`：`rule_id` + `path_pattern`（文档目录） | 不要全局关闭 AWS-AKID；示例值尽量改成 `AKIA...EXAMPLE` 等明确占位符 |
| 2 | 测试夹具 / 快照中的合成密钥 | Secret 各类 | 夹具需要符合真实格式才能测试检测器 | `allowlist`：规则 + `tests/**/Fixtures/**`；或 `exclude.paths` 整目录不扫描 | 只有确认该目录永不包含真实凭据时才用 `exclude`；否则白名单更可审计 |
| 3 | 隐私测试数据（手机号 / 身份证 / 银行卡） | `GGD/PRIVACY/*` | 合成号码符合格式与校验位 | `allowlist`：规则 + 测试目录；断言用的固定值可用指纹条目 | 测试数据必须明显虚构；真实客户数据禁止进入仓库 |
| 4 | 文档中的本地绝对路径 | `GGD/LOCALPATH/WIN-USER` / `UNIX-HOME` | 文档演示安装路径 | 文档路径已自动降一级且 Low 规则在文档 glob 下不产生 Finding；Markdown 围栏代码块内整行跳过（`GGD-0040`，支持反引号 / 波浪线围栏）；围栏外仍有命中时用规则 + 文档路径白名单 | 不要把整个 `docs/**` 排除，文档仍应扫描真实密钥；跨 unified-0 差异缺口时围栏状态不可知，会保守回落为正常检测 |
| 5 | `docker-compose` / 示例配置中的内网 URL | `GGD/URL/PRIVATE-IP` / `LOCAL-HOSTNAME` | 示例环境使用 `192.168.*` / `*.internal` | 规则 + 文件路径白名单（通常为 Medium，仅警告） | 若整个仓库的内网地址都是公开设计，可评估禁用该规则，但需安全负责人审批 |
| 6 | 示例配置中的密码 / JWT / 连接串 | `GENERIC-PASSWORD` / `JWT` / `DB-CONN-STRING` | 示例账号密码、演示 JWT、模板连接串 | 改成占位符（`<password>`、`${DB_PASSWORD}`）；确认无效后按规则 + 路径白名单 | 不要把真实口令改个名字继续提交；真实口令必须轮换 |
| 7 | 锁文件 / 压缩产物 / 第三方代码 | 多类规则 | 非人类维护内容，噪声高且不应修改 | `exclude.files`（`*.lock` / `*.min.js`）或 `exclude.paths`（`vendor/**`、`node_modules/**`） | `exclude` 的文件完全不参与扫描、不产生 Finding，也可能漏掉真实凭据；只用于生成物 / 第三方目录 |
| 8 | 文档中的邮箱地址 | `GGD/PRIVACY/EMAIL` | 公开联系人邮箱被 Low 规则命中 | Low 仅警告，可保留；噪声大时规则 + 文档路径白名单 | 不要全局禁用邮箱规则，代码中的真实个人信息仍需发现 |
| 9 | 手机号 / 身份证号被业务 ID 误命中 | `GGD/PRIVACY/CN-MOBILE` 等 | 长数字串恰好符合格式，上下文关键字又碰巧出现 | 指纹白名单（单值）；或规则 + 具体文件路径 | 若同类值大量出现，考虑禁用内置规则并用更严格的自定义规则替换 |
| 10 | Azure / AWS Secret 熵值命中 | `AZURE-STORAGE-KEY` / `AWS-SECRET` | Base64 串符合长度与熵要求 | 规则 + 配置样例路径白名单 | 先确认不是真实密钥；真实密钥按 TP 处理 |
| 11 | 测试证书中的 PEM 私钥 | `GGD/SECRET/PRIVATE-KEY` | 测试 TLS 证书包含私钥块 | 规则 + 测试证书路径 / 指纹白名单 | 确认该私钥仅用于测试且无生产权限；否则按 TP 轮换 |
| 12 | Gitleaks 与内置规则重复或 Gitleaks 独有误报 | `GLK/SECRET/*` | 两个引擎对同一值给出不同规则 ID | 重复命中已自动去重；独有误报用 `disabled_rules` 精确禁用 `GLK/` 规则 | 禁用整个 Gitleaks 适配器是最后手段，会失去其覆盖能力 |

## 5. 白名单治理

### 5.1 匹配语义与来源

白名单条目包含三个可选条件：`rule_id`、`path_pattern`、`fingerprint`。

- 三个条件中至少声明一个；声明的条件必须**全部匹配**（AND），未声明的条件视为通配。
- 任一条目匹配某 Finding，该 Finding 被标记为 `Allow + IgnoredByAllowlist`，**仍会出现在报告与审计中**，不会被删除。
- `path_pattern` 使用仓库相对路径（`/` 分隔）的 glob：`*` 段内任意字符、`?` 段内单字符、`**` 独立段匹配零或多层目录，大小写敏感。
- 白名单条目当前**没有过期时间**（CLI 不接受 `--expires-at`，配置文件也不支持），必须靠定期复核清理。
- 白名单来源有两个，扫描时合并生效：
  - **项目级 `.gitguard.yml` 的 `allowlist.entries`**：随仓库提交、可 Code Review、团队共享；
  - **本机 SQLite `allowlist` 表**：通过 `gitguard allowlist add/remove/list` 管理，只影响当前用户 / 机器。
- 审计库读取失败按 FailClosed 处理（退出码 14），不会静默忽略白名单。

**可移植性关键约束**：指纹是使用每用户本地盐计算的 HMAC-SHA256。把 `fingerprint` 写进共享的 `.gitguard.yml` 后，换一台机器 / 换一个用户就匹配不上。因此：

- 指纹条目只写本机 SQLite，不写项目配置；
- 团队共享配置只使用 `rule_id` / `path_pattern`；
- 基线文件同理，只在本机生成、本机消费，不要提交到仓库。

### 5.2 粒度选择

| 粒度 | 写法 | 适用场景 | 影响面 | 可移植性 | 建议 |
| --- | --- | --- | --- | --- | --- |
| 指纹 + 规则 + 路径 | `--rule` + `--path` + `--fingerprint` | 单个已确认的误报值，且希望限制在特定目录 | 最小 | 仅本机（指纹） | **首选**；用于一次性、已核实的误报 |
| 规则 + 路径 | `--rule` + `--path` | 某条规则在整个目录内系统性误报（文档示例、夹具） | 小 | 可共享 | **团队配置首选** |
| 仅路径 | `--path` | 整个目录内所有规则都无需阻断（生成物、第三方代码） | 大 | 可共享 | 慎用；优先 `exclude`（完全不扫描）或加规则条件 |
| 仅规则 | `--rule` | 该规则在本项目内完全不可用 | 全局 | 可共享 | 尽量避免；应改为 `disabled_rules` 并记录审批 |
| 仅指纹 | `--fingerprint` | 同一条误报值在多个位置出现 | 中 | 仅本机 | 可用于本机治理；不要写入共享配置 |

命令示例：

```bash
# 团队共享：文档目录中的 AWS 示例值
gitguard allowlist add --rule GGD/SECRET/AWS-AKID --path "docs/examples/**" --reason "误报：AWS 官方文档示例值；票据=SEC-101；责任人=张三；复核=2027-01-15"

# 本机：单个已核实的误报值
gitguard allowlist add --rule GGD/PRIVACY/CN-MOBILE --fingerprint <64位HMAC指纹> --reason "误报：合成测试号码；票据=SEC-102；责任人=李四；复核=2027-01-15"

# 查看与删除
gitguard allowlist list --limit 50
gitguard allowlist remove --id <条目 GUID>
```

### 5.3 原因模板与审批

`reason` 必填，trim 后 5 ~ 256 字符。推荐统一格式，便于审计与到期清理：

```text
误报：<具体原因，说明为什么不是真实敏感信息>；票据=<缺陷 / 安全工单 ID>；责任人=<姓名>；复核=<YYYY-MM-DD>
```

要求：

- 不得写入完整敏感值、完整手机号 / 身份证号或任何个人隐私原文；可引用脱敏片段或指纹前缀。
- 每条共享白名单必须经过 Code Review；评审人确认「值确实为假 / 已失效 / 无权限」后才合并。
- SQLite 本机条目由使用者自行登记，但同样要填写票据与复核日期；安全管理员可导出 / 抽查。
- 新增、删除白名单都会写 `AllowlistChanged` 审计事件（含条目 ID、动作、规则、路径、指纹、原因），可用于追溯。

### 5.4 定期复核

- 试用首月：每周复核一次；稳定后：至少每季度一次。
- 复核内容：条目是否仍必要、对应工单是否关闭、原因是否仍成立、路径是否仍存在、责任人是否在职。
- 清理流程：`allowlist list` → 逐条核对 → `allowlist remove --id <GUID>` → 对相关仓库执行一次 `scan --all` 或暂存扫描，确认没有重新引入阻断。
- 发现条目掩盖了真实凭据时：立即删除条目、轮换凭据、按安全事件流程处理，不得只删除条目了事。

### 5.5 禁止事项

1. 禁止用白名单放行真实可用的凭据；白名单只解决「检测噪声」，不解决「泄漏」。
2. 禁止使用 `--rule` 单独放行 Critical 级 Secret 规则（如 `GGD/SECRET/PRIVATE-KEY`）。
3. 禁止使用 `--path "**"`、`--path "*"` 等全仓库路径。
4. 禁止把 `fingerprint` 条目提交到共享 `.gitguard.yml`。
5. 禁止直接修改 SQLite `allowlist` 表；所有变更必须走 CLI，以保证审计事件。
6. 禁止用 `exclude` 隐藏应当扫描的业务代码；`exclude` 只用于生成物、第三方依赖、明确无敏感信息的夹具目录。
7. 禁止用基线文件压制新产生的 Finding；基线只用于已确认的历史存量噪声。
8. 禁止在 `reason` 中记录原始敏感值或个人隐私。

### 5.6 治理手段对比

| 手段 | 生效范围 | 是否产生 Finding | 报告中的表现 | 可移植性 | 典型用途 |
| --- | --- | --- | --- | --- | --- |
| `exclude.paths` / `exclude.files` | 所有扫描 | 否（扫描前丢弃） | 完全不出现，不计 `files_scanned`，不计 `skipped_files` | 随配置共享 | 生成物、依赖、第三方、确定无敏感内容的夹具 |
| 白名单（配置 / SQLite） | 所有扫描 | 是 | `Allow + IgnoredByAllowlist`，保留可追溯记录 | 规则 / 路径可共享；指纹仅本机 | 已确认的误报，希望保留审计痕迹 |
| 基线文件 | 仅 `scan --all` 默认消费 | 是 | `Allow + IgnoredByBaseline` / `AllowedByBaseline` | 仅本机（本地盐） | 历史存量噪声，不阻断全量扫描 |
| `policy` / `disabled_rules` | 所有扫描 | 规则关闭则不产生；策略降级仍产生 | 策略降级改变 action；禁用规则完全不出现 | 随配置共享 | 全局策略调整，需审批；不是日常误报处理手段 |

补充：

- `exclude` 静默跳过，适合「本就不该扫描」的内容；白名单保留 Finding，适合「扫描到了但确认是误报」。
- 基线文件只影响 `scan --all`，不会让 `pre-commit` / `pre-push` 放行；不要指望用基线解决提交时的噪声。
- `policy` 是严重度级全局开关；`disabled_rules` 是规则级全局开关。两者都会产生 `PolicyOverride` 审计事件，变更必须走配置评审。
- `rules.url.public_hostname_whitelist` 是 URL 类别的主机级降噪（精确主机或 `*.example.com`），命中不产生 Finding、也不留审计记录；仅用于可信公共文档主机，不要用它掩盖内网地址或带凭据的 URL。
- Markdown 围栏代码块感知仅作用于 LocalPath：`.md` / `.markdown` 中围栏内的行整行跳过，不产生 Finding、不留审计记录；unified-0 差异缺少围栏上下文时保守回落为正常检测，此时仍需按常规手段处置。

## 6. 误报率统计方法

### 6.1 数据来源与导出

所有统计基于本地审计库。先导出 CSV：

```bash
# Git Bash / Linux / macOS
mkdir -p artifacts/acceptance
# PowerShell：New-Item -ItemType Directory -Force artifacts/acceptance | Out-Null
# cmd：mkdir artifacts\acceptance
gitguard audit export --output artifacts/acceptance/audit.csv --format csv
```

CSV 表头固定为（单行，下列仅为排版换行）：

```text
run_id,repo_path,scan_type,started_at,duration_ms,result,exit_code,finding_id,rule_id,file_path,line_number,severity,fingerprint,snippet_masked,commit_sha
```

字段使用说明：

| 字段 | 用途 | 注意事项 |
| --- | --- | --- |
| `run_id` | 关联 `gitguard audit view <run-id>` 查看上下文 | 文本报告不直接给 run_id 时用 `audit list` 查最近运行 |
| `repo_path` | 筛选试用仓库 | 导出包含本机所有仓库，必须按路径过滤 |
| `scan_type` | 限定 `PreCommit` / `PrePush` | 排除 `Manual`（历史全量）与 `Bypass`（无 Finding） |
| `started_at` | 限定首周时间窗 | UTC ISO 8601；按本地时区换算后固定窗口 |
| `result` | 运行结果 | `Blocked` 只说明运行被阻断，不代表每一行都是阻断级 |
| `rule_id` | 单规则统计 | 与 `rules list` / `rules view` 对照规则分级 |
| `severity` | 还原阻断级集合 | 导出没有 `action`；用试用期冻结的策略映射 |
| `fingerprint` | 唯一问题去重 | 64 位小写十六进制；同值跨文件 / 跨提交稳定 |
| `snippet_masked` | 人工初筛 | 已脱敏，禁止尝试还原原文 |
| `commit_sha` | 定位历史提交 | 暂存扫描通常为空 |

导出文件含脱敏片段、文件路径与指纹，仍属于内部数据：按公司数据分级保存，不上传外部服务，不粘贴到公开 Issue。

### 6.2 评审表

建议在试用仓库之外维护一份评审表（Excel / 内部表格），每个唯一问题一行：

| 列 | 说明 |
| --- | --- |
| `issue_key` | `rule_id + ":" + fingerprint` |
| `first_seen` | 首次出现日期（UTC） |
| `rule_id` | 规则 ID |
| `severity` | 原始严重度 |
| `file_path` | 首次出现的文件路径 |
| `snippet_masked` | 脱敏片段（仅供定位） |
| `classification` | TP / FP / Pending |
| `reason` | 判定依据（不得含原文） |
| `disposition` | 修复 / 白名单 / 排除 / 基线 / 规则调整 / 无需处理 |
| `ticket` | 工单号 |
| `reviewer` | 评审人 |
| `reviewed_at` | 评审日期 |

评审时优先看阻断级 Finding：每条都要在 1 个工作日内给出分类。Medium / Low 可批量初筛，但抽样比例与抽样方法要记录。

### 6.3 计算步骤

1. 从 CSV 过滤：`finding_id` 非空、`repo_path` 属于试用仓库、`scan_type ∈ {PreCommit, PrePush}`、`started_at` 在窗口内。
2. 按 `(rule_id, fingerprint)` 去重，保留最早一行作为唯一问题。
3. 按评审表补齐 `classification`。
4. 按冻结策略计算 `block_set`（默认 `Critical` + `High`）。
5. 计算 M1 ~ M5，并记录分母、分子、Pending 数与评审完成率。
6. 按规则汇总 M4，取样本量 ≥ 5 的前 5 条规则列入报告。

### 6.4 计算示例

假设首周窗口内：

- 全部唯一问题 120 条：TP 102、FP 12、Pending 6；
- 其中阻断级唯一问题 80 条：TP 72、FP 8、Pending 0；
- 阻断级事件行 210 行，其中对应 FP 的事件 14 行；
- `GGD/PRIVACY/CN-MOBILE` 唯一问题 18 条：TP 13、FP 5。

计算：

| 指标 | 计算 | 结果 |
| --- | --- | --- |
| M1 阻断级问题误报率 | 8 / (72 + 8) | **10.0%**（≤ 10%，达标） |
| M2 全量问题误报率 | 12 / (102 + 12) | 10.5% |
| M3 阻断级事件误报率 | 14 / (196 + 14) | 6.7% |
| M4 CN-MOBILE 单规则误报率 | 5 / (13 + 5) | 27.8%（需专项治理） |
| M5 待定率 | 6 / 120 | 5.0%（处于边界，建议补完评审） |

> 示例仅用于说明算法，不代表真实项目数据。若 M5 超过 5%，先补评审；若 M1 超过 10%，不得四舍五入为达标。

### 7.6 未达标时的处理

1. 取 M4 排名前 3 的规则，逐条分析误报原因（上下文不足、路径过宽、规则本身过泛）。
2. 优先修复内容或增加上下文 / 路径白名单；必要时禁用单条规则并登记审批。
3. 修复后从下一个工作日重新开始 5 个工作日窗口，不沿用旧窗口数据。
4. 若因项目本身包含大量不可避免的真实敏感数据（如安全研究仓库），应更换试用项目，而不是把误报率统计口径改宽。
5. 回滚：`gitguard uninstall` 移除 Hook；白名单 / 审计数据保留在本机，不删除；回滚前记录未决 Finding。

## 8. 处置手册与命令速查

### 8.1 发现误报后的标准动作

1. **复现**：确认命中的扫描类型（暂存 / 推送 / 全量）与规则 ID。
2. **定位**：`gitguard audit list --result Blocked --limit 20` 找到 `run_id`，再执行 `gitguard audit view <run-id>` 查看脱敏明细与指纹。
3. **判定**：按 §2.2 分类；真实凭据按 TP 流程处理，不进入白名单。
4. **治理**：按 §4 的首选顺序选择 `exclude` / 白名单 / 基线 / 规则调整；共享配置走 Code Review。
5. **验证**：重新执行对应扫描，确认不再阻断或仅保留可接受的警告；在评审表登记 `disposition` 与工单号。

### 8.2 常用命令

```bash
# 扫描
gitguard scan --staged
gitguard scan --push
gitguard scan --all
gitguard scan --all --include-history
gitguard scan --all --baseline .gitguard-baseline.json

# 审计查询
gitguard audit list --limit 20 --offset 0
gitguard audit list --result Blocked --since 2026-10-22
gitguard audit view <run-id>
# Git Bash / Linux / macOS；PowerShell 用 New-Item -ItemType Directory -Force artifacts/acceptance
mkdir -p artifacts/acceptance
gitguard audit export --output artifacts/acceptance/audit.csv --format csv

# 白名单
gitguard allowlist add --rule GGD/PRIVACY/EMAIL --path "docs/examples/**" --reason "误报：示例邮箱；票据=SEC-101；责任人=张三；复核=2027-01-15"
gitguard allowlist list --limit 50 --offset 0
gitguard allowlist remove --id <条目 GUID>

# 规则查看
gitguard rules list --category Secret --enabled
gitguard rules view GGD/SECRET/AWS-AKID
gitguard rules view GGD/SECRET/AWS-AKID --show-pattern
```

全局 `--format json` 必须放在 `audit` / `allowlist` / `rules` 之前（如 `gitguard --format json audit list`）；`audit export` 后面的 `--format` 是导出文件格式。

### 8.3 配置片段

排除生成物（所有扫描均不进入检测）：

```yaml
version: 1
exclude:
  paths:
    - "**/bin/**"
    - "**/obj/**"
    - "**/node_modules/**"
    - "vendor/**"
  files:
    - "*.lock"
    - "*.min.js"
    - "package-lock.json"
```

团队共享白名单（只用规则 + 路径）：

```yaml
version: 1
allowlist:
  entries:
    - rule_id: GGD/SECRET/AWS-AKID
      path_pattern: "docs/examples/**"
      reason: "误报：AWS 官方文档示例值；票据=SEC-101；责任人=张三；复核=2027-01-15"
```

精确禁用规则（需审批并记录）：

```yaml
version: 1
rules:
  url:
    disabled_rules:
      - GGD/URL/LOCAL-HOSTNAME
```

| 退出码 | 场景 | 误报治理中的含义 |
| --- | --- | --- |
| 0 | 扫描通过 / 命令成功 | 无阻断；警告仍可能存在 |
| 1 | 业务阻断 | 有阻断级 Finding；进入评审流程 |
| 7 | 用法错误 | 命令参数写错，检查 `--help` |
| 13 | 配置 / 基线读取失败 | 修正 YAML 或重新生成基线，不静默跳过 |

| 40 | 规则不存在 | 用 `rules list` 确认规则 ID |
