# ADR-0001：GitGuard 采用模块化单体架构

- **状态**：Accepted
- **决策日期**：2026-10-15
- **决策人**：王如生（项目负责人）
- **关联文档**：`03-系统架构设计(SAD).md` §3 架构原则 / §5 逻辑架构
- **关联需求**：`NFR-P-001`（冷启动）、`NFR-A-001`（Hook 兼容）、`NFR-M-001`（可维护性）

## 背景

GitGuard 作为**本地 Git 敏感信息防泄漏工具**，核心运行形态是单进程 CLI（Native AOT）+ 可选桌面端（Avalonia）。决策时的处境：

- MVP 阶段只有 1 位开发者维护；没有运维团队，也没有服务器基础设施。
- 用户感知度排名：**启动速度 > Hook 兼容性 > 功能完备性**。
- 域边界清晰但较简单：检测 / 策略 / Hook / 审计 / CLI；无跨服务编排需求。
- 未来可能加入桌面端复用 Core / Application，但不改变单进程部署形态。

## 决策

采用**模块化单体（Modular Monolith）**作为 v0.x ~ v1.x 阶段的主架构：

- 单一发行物（Native AOT 单文件 CLI；桌面端为同源可选发行物）。
- 内部按模块强分层：`Core`（领域规则）、`Detection`（检测器）、`Application`（用例编排）、`Infrastructure`（Git / SQLite / FS / Logging）、`Cli`、`Desktop`。
- 模块间通信只允许通过 `Core.Abstractions` 定义的接口；跨层私有访问由 Analyzer 规则禁止。
- 保留分离的可能：`IDetector` / `IAuditStore` / `IGitAccess` / `IRuleSource` 均为抽象接口，未来若要把检测器拆到独立进程、或把审计换成服务端共享，核心逻辑无改动。

## 影响

### 正面

- **冷启动极快**：单进程 + Native AOT 可达 ≤ 150ms，满足 Hook 调用的高频触发体验。
- **零运维**：无需 Docker / Kubernetes / 消息队列；用户 `install` 即用。
- **调试简单**：所有执行在同一个进程内，可直接 attach 调试器。
- **跨模块重构零成本**：不涉及跨服务协议版本化问题。

### 负面

- **桌面端无法独立扩容**：桌面端复用 Application 后，若桌面端引入耗时的任务可能影响 CLI 冷启动（代码共享）。实际风险低，因为桌面端是独立项目（`GitGuard.Desktop`），不会被 CLI 项目引用。
- **边界腐化风险**：若未执行 Analyzer 规则，上层会直接 `new` 下层实现，拆分成本陡增。
- **规则库规模增大后，发行物体积会同步增大**；Native AOT 下文件可能从 ~10 MB 增长到 ~30 MB（可接受）。

### 需要配套的实践

- 在 `GitGuard.sln` 的所有项目 `csproj` 中强制依赖方向（见 SAD §5）。
- 添加 Roslyn Analyzer 或自写规则：`Cli` / `Desktop` 项目不得引用 `Infrastructure`。
- 规则库增长到一定规模时，考虑拆出 `GitGuard.Rules`（纯 YAML 包）与运行时解耦，避免代码增编规模线性增长。

## 替代方案

### 方案 A：微服务（CLI → gRPC Daemon → 多个服务）

- **优点**：模块天然边界清晰；可按需拆分规则引擎与审计存储。
- **未采纳原因**：
  - 本地场景引入 Daemon 需要启动/停止/升级流程，用户体验差。
  - 跨进程通信抹掉了 Native AOT 冷启动的收益。
  - 单人维护无力承担。

### 方案 B：单一大单体（无模块划分）

- **优点**：开发最快。
- **未采纳原因**：规则与策略耦合将快速劣化为「屎山」；桌面端复用成本高；无法单独测试 `Core`。

### 方案 C：Serverless 函数

- **优点**：零运维。
- **未采纳原因**：GitGuard 是**本地**工具，运行在开发者机器上；Serverless 场景不适用（这是一个概念性替代，用于佐证选项完整性）。
