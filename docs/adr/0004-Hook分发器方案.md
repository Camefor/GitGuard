# ADR-0004：Hook 分发器方案（兼容 Husky / lefthook / 既有 Hook）

- **状态**：Accepted
- **决策日期**：2026-10-15
- **决策人**：王如生（项目负责人）
- **关联文档**：`模块设计/Hook.md` / `02-SRS §2.1`
- **关联需求**：`FR-010, FR-011`、`DR-05`

## 背景

Git 对单一仓库每个 Hook 名称只认一个脚本文件。真实项目往往已经通过：

- Husky（Node.js 生态常见）
- lefthook（Go，跨语言）
- pre-commit（Python，`pre-commit-hooks`）
- 公司自写脚本

安装了 `.git/hooks/pre-commit` 等 Hook。GitGuard 若直接覆盖，会**静默破坏既有流程**（违反 DR-05 并严重影响用户信任）。

此外，较新的 Git（≥ 2.37）引入 `git config set hook.<name>.command ...` 新机制，但当前覆盖率不足以作为唯一方案。

## 决策

采用 **「分发器脚本（Dispatcher）」模式**：

1. GitGuard 的「Hook」实际是一个薄分发脚本，首行注释为 `# gitguard-managed vX.Y.Z` 作为识别标签。
2. 分发脚本的职责：
   a. 调用 GitGuard CLI（固化绝对路径到脚本内）；
   b. 若存在原备份 `<hook>.local.bak`，使用 `exec` 调用并保留退出码；
   c. 返回「GitGuard 退出码」和「原 Hook 退出码」中的非零项（任一失败即阻断）。
3. 安装流程 (`gitguard install`)：
   - 检测 `core.hooksPath` 和默认 `.git/hooks/`。
   - 对 `pre-commit` / `pre-push` 分别：
     - **不存在** → 直接写入分发脚本。
     - **已存在且带 `gitguard-managed` 标签** → 覆盖为新版本脚本（用户无感升级）。
     - **已存在但未托管** → **必须备份**到 `<hook>.local.bak`；若用户加 `--force` 才覆盖。
4. 卸载流程 (`gitguard uninstall`)：
   - 若有备份 → 还原 `<hook>.local.bak` 为原名。
   - 若无备份 → 删除分发脚本。
   - 记录 `HookInstalled/Uninstalled` 审计。

## 影响

### 正面

- 完全兼容 Husky / lefthook / pre-commit / 公司脚本；用户无感。
- 升级 GitGuard 版本时自动替换分发脚本，无需用户干预。
- 卸载时精准还原原有状态。
- `gitguard status` 可展示整个调用链。

### 负面

- 调用链多一层子进程启动开销（可忽略，≤ 5ms）。
- 若用户手动改分发脚本内容，升级时会被覆盖（通过 `gitguard-managed` 标签明确告知「不要手改」）。
- 分发脚本的 Shell 兼容性需要在 Windows Git bash / Unix sh / macOS zsh 均验证。

### 配套机制

- 分发脚本模板位于 `src/GitGuard.Application/Hooks/Templates/`。
- Unix 版本为 sh（Git for Windows 自带 MSYS2 bash）。
- 若未来需要支持 PowerShell 版本，追加 `.ps1` 变体，`gitguard install` 自动选择。

## 替代方案

### 方案 A：直接覆盖已有 Hook

- **优点**：最简单。
- **未采纳原因**：违反 DR-05；用户信任崩塌。

### 方案 B：拒绝安装（遇到已有 Hook 退出）

- **优点**：零破坏。
- **未采纳原因**：无法进入已经使用 Husky 的真实项目；采用率极低。

### 方案 C：仅使用 `git config set hook.<name>.command`

- **优点**：现代化方案；多 Hook 可共存。
- **未采纳原因**：Git ≥ 2.37 才支持；覆盖面不足以作为唯一方案。可作为未来增强，但不替代传统方案。

### 方案 D：要求用户通过 Husky 配置里引用 `gitguard`

- **优点**：无需覆盖 Hook 文件。
- **未采纳原因**：
  - 要求用户熟悉其 Hook 工具的配置机制。
  - 用户没装 Husky 时无方案。
  - GitGuard 失去「一键安装」的用户体验。

## 备注

- 分发器方案是业界常见做法；类似 `pre-commit` 工具的「跨工具嵌入」也采用等价模式。
- 若未来 Git 原生支持多 Hook 调用链（`hook.<name>.command` 多重注册），本 ADR 可能被 Superseded。
- **实施说明（GGD-0008）**：
  - 分发脚本最终**未采用 `exec` 调用备份**（决策第 2b 条原设想）：`exec` 会替换 shell 进程、跳过后续退出码合并；改为直接调用并以「GitGuard 非零优先，否则沿用原 Hook 退出码」合并（任一失败即阻断，与第 2c 条意图一致）。
  - 备份采用**复制**（`File.Copy`）而非改名：卸载还原依赖备份在安装期间原位保留；非 Windows 平台显式对齐源文件 Unix 权限位（分发脚本以 `[ -x ]` 门控）。
  - `--force` 语义收敛为**仅接管二进制 / 符号链接**；普通文本 Hook 自动备份包裹，无需 `--force`（决策第 3 条 bullet 的「若用户加 `--force` 才覆盖」以本条为准）。「遗留 `.local.bak` + 非托管目标」冲突即使 `--force` 也拒绝，防止覆盖真正的原 Hook。
  - 分发脚本仅提供 POSIX sh 形态；PowerShell 变体（配套机制 §「若未来需要支持」）当前撤销，Git for Windows 由自带 MSYS2 sh 覆盖。
  - 安装 / 卸载共用 `<git-common-dir>/gitguard.install.lock` 独占锁，冲突退出码 50；安装采用三阶段（预检全部 → 渲染全部 → 写入全部）保证零半安装。
