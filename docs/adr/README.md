# 架构决策记录（ADR）

> **说明**：本目录保存 GitGuard 项目关键决策的记录。ADR 回答「我们当时为什么这样决定」，是未来回看决策合理性的证据链。小改动不写 ADR；影响架构、依赖、合规、成本或长期演进的决策必写。

## 1. 什么该写 ADR

- 技术选型（语言、框架、数据库、通信协议、密钥管理方案等）。
- 架构模式（分层策略、单体 vs 微服务、同步/异步、CQRS、事件驱动）。
- 不可逆或迁移成本高的决定（数据模型、CLI 契约、公开接口兼容策略）。
- 合规 / 安全 / 商业约束影响工程设计的决定。
- 推翻之前已登记的 ADR（新 ADR 应引用并明确 Supersedes）。

## 2. 什么**不**该写 ADR

- 命名风格、代码格式等编码规范（在 `13-开发规范.md`）。
- 单一 Bug 的修复思路（在 PR 描述或 Issue 里）。
- 尚未执行的脑暴（先讨论，达成一致后再写 ADR）。
- 短期实验或 PoC（结束后如选用才写 ADR）。

## 3. 编号规则

- 编号四位数：`0001` 开始，顺序递增，不复用。
- 文件名：`<编号>-<中文或英文短语>.md`，例如 `0001-采用模块化单体架构.md`。
- 不随 Supersedes 重编号，原 ADR 保留并标记状态。

## 4. 状态机

- `Proposed`：提案中，等待评审。
- `Accepted`：已通过，正在执行或已执行。
- `Rejected`：评审后决定不采纳，但保留以备复盘。
- `Superseded by ADR-XXXX`：被新 ADR 替代，保留原文。
- `Deprecated`：曾经执行但现在不再推荐，无直接替代。

## 5. 如何写一份 ADR

1. 复制任一已存在 ADR 作为模板。
2. 修改编号 + 标题。
3. 填写背景、决策、影响、替代方案、后续动作。
4. 状态设为 `Proposed`。
5. 评审通过后改为 `Accepted` 并同步相关文档（SAD §2、模块设计、相关规范）。

## 6. ADR 与其他规约的关系

| 规约 | 用于 | 本目录的责任 |
| --- | --- | --- |
| `FR-*` | 产品功能需求 | ADR 可引用 FR 作为背景 |
| `NFR-*` | 非功能需求 | ADR 的影响评估需说明 NFR 变化 |
| `DR-*` | 领域规则 | 规则本身在 DDD，不写 ADR |
| `ADR-*` | 架构决策 | 本目录唯一记录处 |
