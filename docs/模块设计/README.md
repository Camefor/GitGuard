# 模块设计

> **填写指南**：本目录存放本项目**核心业务模块**的详细设计文档。00-18 主干文档描述跨模块的通用关注点（架构、数据、API、规范、部署）；具体业务规则、数据流、算法、Provider 适配等**模块级细节**在本目录展开。

## 1. 本目录的作用

- 承载业务领域中可独立讨论、独立演进的模块文档。
- 与 `04-领域模型设计(DDD).md` 的限界上下文一一对应或细化到聚合级。
- 作为 PRD / SRS 的 FR-NNN 落地到可实施模块设计的桥梁。

## 2. 什么该拆为独立模块文档

- 已识别为独立限界上下文或聚合（见 `04-DDD`）。
- 承担跨多个用户场景的核心规则（如风险判定、评分、匹配、推荐）。
- 对接独立的外部数据源 / 第三方服务（如多个 Provider 的接入与标准化）。
- 独立演进节奏（算法/规则/数据模型会频繁迭代）。

## 3. 什么**不**该拆为模块文档

- 跨所有模块的通用关注点（已在 00-18 主干文档覆盖）。
- 单一 FR 的局部细节（在 SRS 或代码注释中处理即可）。
- 临时实验或 PoC（在 ADR 中记录决策即可）。

## 4. 命名约定

- 文件名：`<模块名>.md`，使用 CONTEXT.md §2 定义的中文术语。
- 文件数量：建议 ≤ 8 个，超过时考虑是否过细。
- 一个模块一份文档；跨模块的协作文档可以单独命名（如 `模块A与模块B的集成.md`）。

## 5. 怎么新建一份模块文档

1. 复制 [`模块设计模板.md`](./模块设计模板.md) 为 `<模块名>.md`。
2. 从 `04-DDD` 中确认该模块对应的限界上下文 / 聚合。
3. 从 `02-SRS` 筛出该模块承担的 FR-NNN 和 DR-NNN。
4. 填充模板各节；保留每节的「填写指南」直到首次评审通过。
5. 在 `docs/README.md` §2 导航表中添加链接（或在"核心业务模块"一行扩展）。

## 6. 与 00-18 主干文档的关系

| 关注点 | 文档 | 本目录的责任 |
| --- | --- | --- |
| 产品需求 | PRD / SRS | 本目录引用 FR / DR，不重复定义 |
| 架构分层 | SAD | 本目录遵守分层约定，不另立架构 |
| 领域建模 | DDD | 本目录细化到模块级实体 / 规则 |
| 数据表结构 | 数据库设计 | 本目录讨论"为什么需要这些表"，具体 DDL 在 05 |
| 对外 API | API 接口设计 | 本目录讨论业务契约，签名在 06 |
| 测试 | 测试方案 | 本目录列出模块关键测试点，用例在 16 |

## 7. 评审与维护

- 新模块文档首次评审通过前，相关代码不得合入主干。
- 模块设计变更需同步更新本文档与关联的 FR / DR / API / 测试。
- 模块废弃时移入 `_archive/模块设计/<模块名>-<废弃日期>.md`，不删除。
